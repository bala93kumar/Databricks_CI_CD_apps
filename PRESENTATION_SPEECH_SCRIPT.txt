SLIDE 2: ARCHITECTURE STRATEGY - THE TWO-REPO MODEL
--------------------------------------------------------------------------------
[WHAT TO SAY]:
"To start with our high-level architecture, we have implemented an enterprise separation of concerns using two distinct Git repositories.

Our first repo—the one we are demonstrating today—is the Platform & Governance Admin Repo. 
This repository contains zero application code. It is exclusively owned by platform engineers and administrators. It provisions our Azure networking, ADLS Gen2 storage accounts, our DEV and PROD Databricks workspaces, Unity Catalog schemas, and developer access controls.

Our second repo—which we will launch next—is the Developer Pipeline Repo ('pyspark-pipeline'). 
This is where data engineers write PySpark transformations, run local unit tests with pytest, and deploy Databricks Asset Bundles (DABs).

By separating these two concerns, data engineers never need cloud administrative privileges, Azure portal access, or Terraform permissions. They operate safely inside the governance boundaries established by Repo 1."

SLIDE 3: CLOUD INFRASTRUCTURE & FINOPS GUARDRAILS
--------------------------------------------------------------------------------
[WHAT TO SAY]:
"Next, let’s look at the cloud foundation and our strict FinOps controls.

In cloud data platforms, idle standby costs can quickly spiral out of control. For example, a default Azure NAT Gateway costs roughly $32 per month just sitting idle with zero traffic. 
In our design, we implemented custom VNet Injection with zero-NAT networking, utilizing secure Public IP egress during active runs. This gives us an idle standby network cost of exactly ₹0.00 per hour.

Furthermore:
- Our Terraform remote state is stored securely in Azure Blob Storage with automated state leasing and concurrency locks to prevent race conditions during CI/CD runs.
- Storage accounts are isolated per environment: 'dbxdemodev80en' for Development, and 'dbxdemoprod80en' for Production.
- Throughout our multi-day development and testing cycle across both DEV and PROD workspaces, our total cloud spend was under ₹20 total. This proves that an enterprise-grade platform can be maintained at virtually zero standby cost."

SLIDE 4: PILLAR 1 - UNITY CATALOG MEDALLION SCHEMAS AS CODE
--------------------------------------------------------------------------------
[WHAT TO SAY]:
"Now let's examine Pillar 1 of our platform: Unity Catalog Medallion Schemas as code.

In Azure Databricks, when Unity Catalog is auto-enabled in a region like East US, all workspaces share a common regional metastore. To prevent cross-workspace schema pollution, we bound our medallion layers to the dedicated workspace default catalogs.

In this design:
- We declare our medallion schemas—bronze, silver, and gold—in a simple Terraform local map.
- Environmental protection is strictly enforced in CI/CD. When a developer pushes code to the 'dev' branch, GitHub Actions executes targeted plans that touch ONLY the DEV workspace. Production is completely unreachable from the dev branch.
- Production is updated exclusively through a formal Pull Request merged into the 'main' branch.
- And because Terraform is declarative, it automatically handles state reconciliation—creating new schemas and cleanly destroying deprecated ones with zero manual UI intervention."


--------------------------------------------------------------------------------
SLIDE 5: PILLAR 2 - DEVELOPER ONBOARDING & COMPUTE AS CODE
--------------------------------------------------------------------------------
[WHAT TO SAY]:
"Pillar 2 addresses Developer Onboarding, Access Control, and FinOps compute guardrails.

In traditional setups, onboarding a developer involves clicking through multiple Azure AD and Databricks UI menus, which is error-prone and un-audited. 
In our platform, onboarding a developer is as simple as adding their email to a declarative list in Terraform.

Once declared:
1. First, FinOps Guardrail: We set 'allow_cluster_create = false'. Developers are strictly blocked from spinning up multi-node clusters or expensive GPU instances.
2. Second, Automated Compute: The platform automatically provisions a dedicated single-node compute cluster using Standard_D4ds_v4 VMs. We configured a strict 10-minute auto-termination policy. If a developer leaves their desk, the cluster shuts down automatically, ensuring ₹0 idle compute waste.
3. Third, RBAC: In Development, the developer has full write access (CREATE TABLE, MODIFY) to build pipelines. In Production, their account is locked to strictly Read-Only access (USE_SCHEMA, SELECT).
4. Finally, Offboarding: We codified 'force_delete_home_dir = true'. When a developer leaves or is commented out of the code, Terraform automatically deprovisions their user account, revokes all grants, deletes their cluster, and purges their home directory cleanly."

SLIDE 6: PILLAR 3 - DEVELOPER PIPELINE EXECUTION (REPO 2 PREVIEW)
--------------------------------------------------------------------------------
[WHAT TO SAY]:
"Now, how does our second repository—the developer pipeline repo—interact with this platform?

A common question is: How does the new repo inherit permissions from the admin repo?
The answer is that permissions live inside Unity Catalog, not in the Git repository.

Repo 1 established the Unity Catalog schemas and assigned RBAC privileges to our Service Principal.
Repo 2 simply authenticates using that same Service Principal via GitHub Secrets. When the pipeline runs 'databricks bundle deploy', Unity Catalog validates the service principal and allows it to write to marketing_bronze and marketing_silver.

In Repo 2, we also implement 'Shift-Left' quality assurance: PySpark transformations are tested locally with pytest using a local SparkSession inside the GitHub Actions runner. Only when all unit tests pass does the bundle deploy to Databricks."

ANTICIPATED QUESTIONS & ANSWERS (Q&A CHEAT SHEET)
================================================================================

Q1: Why did you choose a Two-Repo model instead of putting everything in a Monorepo?
ANSWER:
"In an enterprise setting, platform governance and application code have completely different lifecycles and security boundaries. Platform engineers manage Azure VNets, IAM, and Unity Catalog schemas, which require elevated privileges. Data engineers write PySpark ETL code and should not have permissions to modify cloud networking or cluster policies. A two-repo architecture enforces least-privilege security and prevents pipeline developers from accidentally destabilizing infrastructure."

Q2: How do you guarantee ₹0.00 idle costs on Azure?
ANSWER:
"Two primary mechanisms: First, on the network layer, we use custom VNet injection with Public IP egress, avoiding the ~$32/month fee of a standby Azure NAT Gateway. Second, on compute, we enforce single-node compute (Standard_D4ds_v4) with a hardcoded 10-minute auto-termination policy. VMs only run when a notebook or job is active, dropping to zero when idle."

Q3: What prevents a developer from creating an expensive GPU or 20-node cluster in DEV?
ANSWER:
"In our Terraform governance code, every developer is provisioned with 'allow_cluster_create = false'. If a developer clicks 'Create Compute' in the Databricks UI, Databricks strictly denies the request. Developers can only attach to pre-approved, admin-managed clusters that have cost guardrails built in."

Q4: How are secrets managed between GitHub Actions and Databricks?
ANSWER:
"We use Azure Service Principal credentials (Client ID, Client Secret, Tenant ID) stored securely inside GitHub Encrypted Secrets. Secrets are injected at runtime into the runner's environment variables and never logged or exposed in code."

Q5: What happens if a developer leaves the company?
ANSWER:
"Offboarding is fully codified. We simply comment out or remove the developer's entry from 'local.data_engineers' in Terraform and merge the PR. Because we set 'force_delete_home_dir = true', Terraform automatically deletes their Databricks user account, revokes all schema grants, deletes their dedicated cluster, and purges their personal workspace folder."
